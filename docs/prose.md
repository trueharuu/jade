Writing Style & Prose

Follow the writing style established by the wirelyre/tetra-tools repository.

The desired voice is plainspoken, terse, technically precise, informal, and understated.

Write like an experienced independent software developer maintaining a personal engineering project. Do not write like a technical writer, corporate engineering team, documentation generator, or AI assistant.

General Style
Be concise. Prefer fewer words.
Use ordinary, natural language.
Be direct and matter-of-fact.
Prefer simple sentence structures.
Use technical terminology naturally, without unnecessarily explaining it.
Sentence fragments are perfectly acceptable when appropriate.
Don't over-polish prose.
Don't make mundane functionality sound impressive.
Don't artificially formalize informal writing.
Allow a little personality and occasional dry humor.
Don't force personality, jokes, or conversational language.
Avoid
Marketing language and promotional descriptions.
Corporate-speak and business terminology.
Excessive adjectives and qualifiers.
Verbose introductory or concluding statements.
Repetitive explanations.
Unnecessary transitions between paragraphs.
Artificially structured prose.
Excessive headings and nested lists.
Generic statements that could describe practically any project.
ChatGPT-style explanations and summaries.
Unsolicited tutorials or educational commentary.
Overly polished, essay-like writing.

In particular, avoid phrases such as:

"It is important to note that..."
"It's worth mentioning that..."
"At its core..."
"This powerful and flexible..."
"Seamlessly integrates..."
"Provides a robust solution..."
"In order to..."
"This ensures that..."
"Whether you're looking to..."
"Let's dive into..."

These phrases are not inherently forbidden when genuinely appropriate, but should almost never appear in ordinary project prose.

README and Documentation
Describe functionality directly.
Prefer short descriptions over paragraphs.
Document actual behavior and limitations.
Don't write promotional introductions.
Don't add sections merely to make documentation appear comprehensive.
Don't explain things that are obvious from the project structure.
Use simple headings.
Keep examples minimal and relevant.
Don't generate documentation unless it serves a real purpose.
Source Comments
Default to no comments.
When comments are necessary, use concise engineering notes.
Explain why, not what.
Avoid conversational or explanatory prose.
Never narrate the implementation.
Don't write comments as miniature documentation articles.
Naming and Descriptions
Prefer short, descriptive names.
Avoid unnecessarily elaborate terminology.
Don't invent abstractions or terminology when ordinary words suffice.
Be comfortable with straightforward, slightly informal descriptions.
Final Rule

Write less. Mean what you write. Don't try to impress the reader.

When deciding between a concise, natural sentence and a polished, elaborate explanation, prefer the concise sentence.

The goal is writing that feels like it belongs in a real developer's repository, not something generated for an audience.
